# Hashtag ordered-search local probe (not a deployment)

The existing hashtag route uses the `unicode61 remove_diacritics 0 tokenchars '#@_'` FTS index to obtain every matching canonical path, then orders and authorizes the result. Ten returned rows do not bound the match scan. A simple SQL LIMIT before sorting or privacy would change results and is not safe.

A throwaway in-memory SQLite experiment used 20,000 synthetic posts, one existing path-based FTS index, and a second contentless FTS index keyed by canonical row ID. It tested a 200-post indexed recent-head candidate window with rowid+MATCH point probes, versus the existing all-match FTS-then-sort query. SQLite VM steps: common tag (all 20,000 posts): 480,125 old versus 11,662 candidate head; rare tag (20 posts total): 521 old versus 8,223 for a head that returned zero; missing tag: 41 old versus 8,223 for the empty head. The candidate head is usable only if it contains a full visible authorized page; otherwise exact existing behavior must be used. These are synthetic VM counts, not Cloudflare billed rows or device savings, and an adaptive fallback still adds work to rare/missing searches.

The extra contentless FTS index occupied about 324 KiB of SQLite pages in this minimal synthetic dataset, excluding other app structures. A guarded duplicate index added local insert 150→265 VM steps, unchanged-metadata update 41→56, content edit 220,215→220,355, and delete 220,169→220,278; the old full-content FTS path itself dominates this simple fixture's edit/delete scan. FTS internals and real D1 write billing are not captured by VM counts. Additional writes/backfill may conflict with the write quota, so this is not grounds to install the index.

An exact production design would also need parity for duplicate old FTS rows, Unicode normalization/token boundaries, nonstandard timestamp/type ranking, ID ordering, every ACL and blocked-author case, deletions and edits, concurrent mutation, schema upgrades, and failure/fallback behavior. These have not been established. No FTS schema, trigger, query behavior or production data was changed by this probe; hashtag all-match materialization remains unresolved.
