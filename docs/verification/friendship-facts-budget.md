# Visible friendship facts: bounded duplicate-safe candidate probes

Home and Friends suggestions need only membership facts for their submitted authors/candidates, not friendship documents. The new authenticated Worker endpoint accepts 1–10 distinct other user IDs, derives the actor from the Firebase token and returns one boolean per candidate. It uses two indexed existence seeks per candidate. Migration `0094_friend_membership_facts.sql` indexes only well-formed two-participant arrays, so neither duplicate relationship documents nor malformed longer arrays cause a page to materialize an unbounded candidate set. Existing ordinary friendship lists and APIs are unchanged. The index is additive and costs an index entry on valid friendship writes.

The Android client validates that every submitted candidate has exactly one boolean fact. Missing, malformed, timed out and obsolete-account/lifecycle responses fail closed. Screen-level in-flight and five-minute Home fact caches remain; the POST is treated as a coalescible read, not a write that invalidates unrelated caches. Invalid candidate IDs are never used to prove absence. Friend-request queries continue to fail closed on saturated pages.

`cloudflare/test/friendship-facts-demand.test.js` seeds 3,000 duplicate rows and 2,000 malformed arrays, checks both participant orderings and third-party isolation, instruments actual matched-row visits, checks the SQLite index plan and verifies a missing index fails closed. This is a deterministic test, not a production D1 billed-read measurement.

**Rollout prerequisite:** migration 0094 must be successfully applied before deploying the Worker endpoint, and that Worker must be live before distributing a client containing this change. A missing endpoint/index leaves these checks unavailable rather than treating people as non-friends. Neither migration nor Worker has been deployed here. Full-app quota and representative-day production correctness remain unproven.
