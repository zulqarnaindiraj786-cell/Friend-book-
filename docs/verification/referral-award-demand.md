# Referral award demand and authority

Main no longer starts a delayed referral count on every new activity. New claims award the inviter at 5/20/50 using canonical referral rows in the same D1 transaction as the claim; the indexed count examines at most 50 rows. The existing count's historical semantics (`refBy`, all canonical rows, not only new claims) are retained. The current profile rank is compared inside the transaction, so existing higher badges are not downgraded. Canonical and mirror profile copies change only on an actual upgrade. Repeated claims and repeated verification-screen status checks make no badge writes when no upgrade is due.

The explicitly opened verification screen asks the Worker to reconcile historical referrals and report a capped progress count and current badge. It no longer attempts a client write to server-owned badge fields. Obsolete screen/account callbacks are ignored. Unknown badge levels and historical wrapped profile records are deliberately left unchanged instead of overwriting potentially meaningful data; they require a separate audited normalization before automatic upgrades can be guaranteed for them. Old denormalized badges on existing content are not rewritten by this change.

`cloudflare/test/referral-award-demand.test.js` exercises historical thresholds, 1,500 extra referrals, sequential no-op repeats, paid-rank preservation, simulated interleavings, a stale claim guard, and atomic rollback on mirror failure. These are local SQLite/Worker tests, not proof of production billing or simultaneous distributed load. A new Worker deployment is required before distributing the corresponding Android client; the referral index from migration 0046 must already exist. No production deployment is performed by this change.
