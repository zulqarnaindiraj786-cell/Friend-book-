Reels also requests `posts WHERE mediaType = 'video' LIMIT 5` with no explicit sort. The previous Worker could load the entire posts root before applying that filter, ACL and limit. `0095_video_post_page.sql` adds a video-only document-ID seek index and a partial malformed-ID exception index. The new Worker path uses ascending document IDs (the existing default ordering), seeks past each cursor, authorizes each canonical row using the existing fresh request-local ACL, and fills pages only as needed. Nonstandard IDs/paths and absent indexes use the existing canonical evaluator; errors fail closed. This improves a concrete Reels consumer without assuming the reported reel-root shape is that post query. Video writes now maintain one additional index entry; exceptional video IDs maintain two. The fallback can still scan the full posts root on nonstandard historical video IDs.

Reels no longer starts a page when its retained fragment starts hidden, on a selected-item callback, or when it merely becomes visible with a short loaded list. The existing **More videos** button explicitly requests the next page; the initial page loads when the fragment is resumed and visible. Hiding or pausing retires in-flight generations and stops their callbacks or filtered-page continuation from starting work. Network requests already sent cannot be recalled. Existing filtered-empty page skipping and manual Retry remain bounded.

Tests: actual Worker + SQLite fixture with 5,000 photo posts and 120 video posts checks page/cursor/ACL parity with the old evaluator, indexed seeks and bounded matched candidates, error fail-closed, fresh block revocation, exceptional IDs and old schema compatibility. The SQLite row observations are not D1 billing. Android source-contract tests check lifecycle/paging wiring; Android compile/JVM CI is required separately.
