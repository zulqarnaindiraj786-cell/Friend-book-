# Create-only notification guard optimization

For Firestore-compatible `PUT` with `createOnly:true` on `notifications/<id>`, the Worker already verifies sender/recipient fields, requires absence in both stores and writes canonical plus legacy copies atomically. Previously it inserted and then deleted a temporary social-guard row for this one create. The canonical insert now tests both stores inside the transaction; a conflicting ID deliberately fails the existing `path NOT NULL` constraint, rolling back both writes. Existing documents still return 409 before the batch. There is no schema migration or Android change. Ordinary `add()` and unrelated notifications do not use this optimization.

Local Miniflare D1 with the real Worker and schema through migration 0080 measured one synthetic create at **1 read / 21 writes / 8 statements** before and **1 / 19 / 4** after. A retry remained **2 / 0 / 2** and returned 409. Two concurrent identical creates returned one 200 and one 409. Synthetic legacy-store collision, mirror-insert failure and forged sender tests preserved the winner, rolled back partial writes and rejected the actor. The local counters include index maintenance but are not account-wide production billing; costs differ by data and workload.

The automated regression additionally covers a canonical-store race, recipient read state, an injected mirror failure and an unauthorized sender. The network-disabled 1,000-user Worker replay ran 999 fresh create-only notifications: SQLite statements **7,992 to 3,996**, changed rows including triggers **3,996 to 1,998**, and returned rows **999 to 999**. The 999 repeated creates returned 409 with zero changed rows in both runs. SQLite change counts do not include index maintenance and are not billed D1 rows. The full replay covered 35,489 synthetic requests and 63 query plans without EXPLAIN errors; it sent no FCM pushes or network requests. Worker tests: 188, schema/plan tests: 9, script tests: 280.

A separate offline repeated-query trace identified reads during story authorization, saved-post authorization and comment acknowledgements. Some apparent repeats recheck privacy, state or the result after a write; none were removed merely because their SQL repeated. This optimization does not eliminate necessary writes, reads, push costs or production quota limits. Rollback is the preceding Worker version; no production fake traffic or schema rollback is needed.
