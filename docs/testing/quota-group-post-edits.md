# Group-post edit quota follow-up

The latest read-only audit reported expensive point-lookup and per-device push-claim shapes, but adaptive analytics does not attribute them to group-post edits. This change targets an avoidable cost found by code inspection; its production frequency and savings are unknown.

A group-post write still authorizes against current group membership and the trusted owner. It now reuses canonical group and post snapshots already obtained by `readRow` rather than reading them again. Both exact snapshots and the trusted owner remain checked by transaction guards; if either changes before commit, the batch aborts and the normal retry reauthorizes. Legacy-only rows retain the canonical/legacy checks. Group-post edits also avoid updating an interaction-resource marker that is already `verified`. Missing or `staging` markers still become `verified`, inside the guarded transaction.

The in-memory SQLite replay was run against identical pre-change and post-change Worker code with 1,000 synthetic users, waves of up to 200 requests, one trusted group, and 1,000 distinct edits whose markers already existed. The group-edit workload used 13,000 versus 11,000 SQLite statements and 30,633 versus 29,633 changed rows including SQLite trigger effects. The difference was 2,000 statements and 1,000 changed rows in this fixture. The full updated replay ran 23,492 requests across 25 workloads, with 31 collected query plans and no plan errors. SQLite statement/change counts omit D1 billing and index-maintenance accounting; they aren't production measurements or a capacity guarantee. Guard rollback, membership revocation, concurrent post edits, legacy-group fallback, verified no-op and staging promotion are covered by tests.

No index or schema migration is needed. This does not cap normal app reads, eliminate push deduplication writes, establish that production requests are mostly group edits, or prove that the overall quota problem is solved. Do not publish the AAB on the basis of this local test alone.
