# Notification bursts and story engagement quota follow-up

The 00:52 UTC read-only adaptive audit found a canonical 32-item notification-window shape at 5,760 rows read / 180 executions in five minutes. This is an adaptive observation, not a controlled experiment and not proof that all executions came from bursty push delivery.

Android prerelease 167 batches notification-list refresh hints for 750 ms per authenticated account. The first hint starts a fixed timer; later hints do not postpone it. When the timer fires, the pending slot is cleared before scheduling an authenticated server refresh, so a later event can schedule another. Different accounts have independent slots and an old account's callback cannot refresh a newly signed-in account. Friend request/friend collection invalidations and chat/call handling remain immediate. Push notifications themselves remain separately delivered; the notification-list refresh can be delayed by up to 750 ms plus network/scheduler delay. Separate committed writes retain their immediate invalidation behavior. Existing APKs do not get this change until updated.

For story views/reactions that would modify data, the Worker reuses the already-read canonical viewer and author profile snapshots during the same request's authorization. The write transaction already guards those exact snapshots, story snapshot and friendship ledger, and retries on races; they remain authoritative at commit. Legacy profiles, invalid state and unchanged canonical engagements retain their previous fresh reads. This avoids two duplicate profile point reads on the applicable changing-write path, not all story reads, and adds no new schema or index writes.

Unit tests cover push bursts, concurrent events, account switching, state reset and Android wiring. Worker tests verify author snapshot reuse, unchanged authorization, a concurrent block and a friendship removal during commit. In the isolated SQLite replay, 999 first story views used 14,985 statements before versus 12,987 after; repeat views were unchanged at 7,992 statements, and changed-row counts were identical. These are local tests and statement counts, not proof of billed D1 rows saved in production. A distributed burst of pushes and individual isolated pushes may see little or no saving. Quota is not bounded under arbitrary workload.
