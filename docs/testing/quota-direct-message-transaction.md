# Direct message send: remove redundant guard writes

The ordinary Android direct-message send batches a new nested message and a room preview/unread update. Previously the Worker added a temporary `friendbook_cf_social_guards` row and then deleted it, even when both the current room and new message were canonical. Each send thus performed two extra D1 row changes for the guard. This was established from the real send path and synthetic Worker tests, not attributed from the shared production SQL upsert shape.

For exactly two `set` operations on an existing canonical direct room and its new nested message, the message INSERT itself checks the authorized room snapshot and absence of the message in both stores. A failed check violates the existing NOT NULL path constraint and rolls back the entire D1 batch. A conflict retries the full read, transforms and authorization, subject to the existing retry limit. The room and, when required, the legacy mirror are still committed in the same batch; group chats, historical-only rooms, root messages, existing messages, other batches and first-room creation retain the old path. Push scheduling remains after the commit. Reordered direct-room participants still update the historical mirror exactly as before. There is no schema migration or Android change.

Tests exercise a successful send, reverse-order reply and mirror, unauthorized sender, concurrent room metadata updates, revocation of membership, a colliding historical message, failure after insertion and failure writing the mirror, with full rollback. A local Miniflare D1 test with all migrations and the real Worker reported 6 rows read / 14 written / 7 statements before and 4 read / 12 written / 5 statements after for one synthetic direct send; it also verified race retry, authorization after revocation and rollback. Those are synthetic local metadata, not actual production billing.

In a separate real-Worker offline SQLite replay, 500 direct sends changed 2,000 rows in 3,500 statements before and 1,000 rows in 2,500 statements after; returned rows were 1,000 in each case. SQLite change counts exclude index maintenance and must not be called billed writes. The full replay ran 33,491 requests, waves up to 200 and 63 collected plans without EXPLAIN errors; database commits were serialized. Worker tests: 182; schema tests: 9; script tests: 280. Reactions, comments, Feed and notifications still have normal costs; these results do not prove their costs are optimal or that all quota issues are resolved. No production artificial traffic or test pushes were used. Rollback is the prior Worker version; the database schema is unchanged.
