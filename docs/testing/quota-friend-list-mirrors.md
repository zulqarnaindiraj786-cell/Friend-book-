# Friendship-list mirror lookup follow-up

The read-only adaptive five-minute audit (run 45003590354) showed a shared friendship candidate SQL shape at 11,770 rows read / 110 executions. The shape is consistent with the participant-scoped list path but cannot identify clients, their parameters, billing, or prove that mirror lookups caused all of those reads. It does not establish the cause of slow loading.

The list path already reads canonical and legacy participant candidates. It now uses matching canonical paths to eliminate their legacy copies without another canonical lookup for each mirror. Legacy candidates absent from the canonical result still undergo bounded primary-key shadow checks in groups of 90, including paths whose canonical record no longer contains the participant. Existing participant indexes, canonical precedence, projection, filtering and authorization remain in place. A failed shadow lookup fails the request rather than exposing stale data. As before, concurrent independent reads are not an atomic snapshot. A legacy-heavy result may require additional query round trips; the change does not guarantee latency improvement. No migration or client change is required.

Offline Miniflare real-Worker comparison of the prior and revised code used 200 matching canonical/mirror pairs and one stale shadowed mirror, querying a 20-document first page. Both returned HTTP 200 with identical ordered IDs and zero writes. Local D1 emulation reported 604 -> 404 rows read and 3 -> 4 statements (the extra statement checks the stale path). This fixture is not production billing, and actual savings depend on the mixture of matching mirrors and traffic. Regression tests cover matching mirrors, 95 legacy-only paths, a stale canonical shadow, 90-parameter batching, permission projection and failed lookup; 212 Worker and nine schema/migration/index tests passed locally. Real-device latency, account-level savings and reaction failures remain unverified.
