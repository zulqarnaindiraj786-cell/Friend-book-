# Unfriend guard write reduction

For the common one-record friendship removal, the Worker now combines its existing three snapshot assertions and exact duplicate-count check into one temporary guard row within the same D1 batch. It does not remove any authorization, historical duplicate, snapshot, mirror or ledger check. Legacy-only records and the missing-index fallback remain supported. Multi-record duplicate removal retains the prior individual guards to avoid parameter-limit regressions. There is no migration or Android change.

In a local Miniflare D1 fixture with the real Worker, migrations through 0084, the indexed guard enabled, and 200 unrelated mirrored friendships, one ordinary removal measured **25 reads / 37 writes / 17 statements → 25 / 31 / 14**. Acceptance stayed 33 / 62 / 20. These are fixture-specific local D1 counts, not measured billed production savings or a quota guarantee. Local Miniflare and SQLite tests checked authorization denial, changes to profile or friendship before the transaction, racing canonical and wrapped legacy duplicates, mirror-delete failure and complete rollback. Two concurrent removals yielded one success and one conflict with correct counters and no duplicate ledger. A 19-record historical removal tests the unchanged multi-guard path.

The network-disabled 1,000-account replay (waves of 200) reduced 100 synthetic unfriend operations from **1,700 to 1,400 SQLite statements** and **1,500 to 900 changed rows** including guard rows; returned rows remained 400. SQLite counts exclude index maintenance and are not billed D1 rows. The complete replay passed 41,888 requests and 70 query plans with no EXPLAIN errors. Local suites passed 209 Worker tests, nine schema/migration/plan tests, and 287 script tests.
