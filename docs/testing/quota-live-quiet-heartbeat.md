# Quiet live-host heartbeat quota follow-up

The Android live host sends a room telemetry update every eight seconds, including the current viewer ID list, peak viewer count and heartbeat time. Before this change, even an unchanged audience updated the canonical D1 room on every pulse. This path is active only while hosting a live; production audit samples have not established how often it runs across users.

The Worker now coalesces the exact authenticated live-host telemetry patch only when the audience and peak are unchanged and the last stored heartbeat is less than 24 seconds old. A fresh canonical snapshot is rechecked before acknowledging a no-op. Audience or peak changes still write immediately; ended/status/privacy edits retain their existing path. Missing, backwards or unusual/future timestamps do not qualify. The response returns the actually persisted state, not a fabricated new heartbeat. There is no per-isolate cache. This increases the maximum timestamp lag by up to 24 seconds; Home, Live Hub and live PK discovery currently use a 150-second stale-room threshold. Client clock errors, failed requests and network pauses can still affect discovery as before. The same code applies to existing clients without an Android release.

In a local Miniflare D1 test with all migrations, one unchanged heartbeat reported 4 reads / 4 writes before versus 3 reads / 0 writes after, each in three statements; a changed audience still reported 4 reads / 4 writes. These are synthetic local metadata, not production billed usage. With no audience changes and reliable 8-second pulses, renewal writes can occur about every 24 seconds instead of every 8; actual results depend on audience changes, clock skew, timing and retries.

A 1,000-host local real-Worker SQLite replay reported 1,000 changed rows before and zero after for 1,000 fresh unchanged heartbeat requests, with 3,000 statements and 3,000 returned rows in both runs. Index-maintenance rows are not included. The complete replay executed 33,491 requests, collected 63 query plans without EXPLAIN errors, and ran in waves of up to 200 against serialized local SQLite. Worker tests 181, schema tests 9 and script tests 278 passed. Tests cover immediate changed audience, the age threshold, non-monotonic/future clocks, unauthorized users and a live end racing the snapshot check. This does not test real video playback, device clocks, production concurrency, or account-wide billed usage. Revert the Worker change if real live-discovery behavior regresses; no migration or data transformation is needed.
