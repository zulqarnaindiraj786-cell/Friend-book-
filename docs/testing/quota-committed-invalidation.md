# Android committed-batch invalidation follow-up

A successful D1 batch or transaction can update many documents in the same collection atomically. Previously each operation separately invalidated its parent collection; for example, a 32-notification batch emitted 32 parent invalidation signals. The existing in-flight guard already coalesced some of those signals, so this does **not** mean the old client necessarily made 32 HTTP requests or consumed 32 times the D1 reads.

After a successful commit, the client now collects unique document paths and parent collections, invalidates all affected document caches, refreshes each affected document listener, then signals each affected collection once. Separate commits and push invalidations are never combined; each still schedules a refresh. Failed commits still produce no invalidation. Moderation also avoids an accidental duplicate parent signal. This makes no change to notification-window size, unread data, call handling, Feed/Reels/Stories page sizes, or Worker authorization. It applies only to an installed Android candidate containing this change; older APKs retain their existing behavior.

Local unit tests cover a 32-item notification batch, multiple collections and nested paths, duplicate paths and separate commits. The Android CI compiles, tests, and produces the signed candidate. This is a reduction in redundant invalidation signals, not a measured production D1 savings figure; effectiveness depends on actual batch traffic and pre-existing in-flight coalescing. It does not prevent quota exhaustion under arbitrary usage and is not a replacement for a bounded server-side projection design.
