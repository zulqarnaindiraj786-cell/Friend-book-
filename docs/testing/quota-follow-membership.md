# Follow-list membership full-scan reduction

Read-only audit 44979139478 showed the legacy users-membership scan shape at 12,570 adaptive reads across 30 executions in its 60-minute window. The normalized SQL identifies the query shape, not the callers or exact filter. Android's follower/following list is one known user of `users` array membership. This sample includes earlier traffic and is not a matched billed comparison.

Aggregate-only preflight 44979510362 found 436 canonical users, 420 legacy users, two legacy-only paths, zero wrapped legacy users, 363 total follower/following array entries across both stores, and a maximum observed array length of 19. The cap was 1,001 per source; it was not reached. D1 reported 6,831 rows read by this investigation. It did not export identities or list entries. The sample is a point-in-time count, not an estimate of billed migration writes. The deployment repeats a conservative capped preflight and aborts migration on truncation, excessive entries, large arrays or too many exceptional rows.

Migration 0077 creates a derived `(member, kind, source, path)` lookup with an index for updating individual paths. It backfills native string membership arrays and atomically maintains candidates via triggers. Wrapped legacy documents and duplicate JSON property names use exception candidates, because SQLite JSON extraction and JavaScript decoding may differ. More than 64 exception rows in either store, missing migration/readiness, a noncanonical path, or a non-ASCII membership value falls back to the existing full scan. The five source/proof reads share a D1 batch snapshot. Canonical path precedence, the existing JS filter, profile privacy projection, ordering and pagination still apply. This indexes both `followers` and `following`; it does not cap either list or change the app's refresh interval. Queries with no suitable array membership filter use the existing paths.

Tests compare the indexed and compatibility paths on over 1,000 users, locked/banned profiles, old-only and wrapped records, stale mirrors, duplicate keys, repeated values, cursor pagination, multi-filter and admin queries, randomized membership changes, invalid paths, exception overflow, missing readiness and Unicode fallback. A profile-only heartbeat changes no derived rows; adding one member to a 300-element synthetic array changed one document and one derived row. Trigger checks still examine arrays when a membership changes: index maintenance has a read/CPU cost and an inserted/deleted edge costs writes. A local 1,000-document synthetic heartbeat experiment estimated roughly 45,000 SQLite VM instructions before vs 465,000 after, with 1,000 changed rows both times; this is not D1 billing or a production latency result.

In a network-disabled actual-Worker replay with 1,000 users, 1,000 follow-list requests returned 2,002,000 SQLite rows in 4,000 statements when forced to the old full scan, versus 21,000 rows in 7,000 statements using the derived lookup; both changed zero rows. The overall run covered 32,491 requests, 34 workloads and 62 plans with no plan errors. SQLite returned rows and statements are not Cloudflare billed rows. Local Miniflare D1 also ran the actual five-query batch and missing-ready fallback. Worker tests: 181; schema/migration/plan tests: 9; script tests: 276. There was no synthetic production traffic or production write verification.

Rollback: an older Worker can ignore the derived table while the triggers continue to keep it current, at maintenance cost. To remove the optimization completely, first deploy an older Worker, then remove the six `cf_user_follow_*` triggers, drop `friendbook_cf_user_follow_index_state` and `friendbook_cf_user_follow_membership`, and verify normal reads. A newer Worker with the tables absent falls back to scanning. Do not drop the membership table while leaving its triggers installed; profile writes would fail. Rebuilding the table or restoring triggers consumes quota and must be planned separately. If migration is partial, inspect its status and trigger definitions before retrying; the readiness marker is set only after backfill and trigger creation.
