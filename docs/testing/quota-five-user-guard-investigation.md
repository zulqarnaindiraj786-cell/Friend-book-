# Five-user quota complaint: real paths, safe receipt guard, and limits

Account-wide read-only analytics on 2026-11-22 at 09:33:37 UTC reported 1,210,926 reads and 53,087 writes for that UTC day. The preceding account sample at 09:17:11 reported 1,202,672 and 52,845, a difference of 8,254 reads / 242 writes across approximately 16 minutes. These are delayed/adaptive account-wide totals, not a live balance or a controlled five-user experiment; they do not explain earlier faster intervals and cannot prove the complaint resolved. The five-minute SQL sample was quiet; a one-minute tail contained one unclassified status-zero event, so it could not attribute normal user traffic. No synthetic production traffic was used.

## A real-path guard

For exactly one canonical nested-message literal read/delivered receipt plus the same direct room's literal unread-count reset, when both rows change, the Worker now checks both authorized document snapshots inside the first write of the same atomic D1 batch. This removes the temporary guard insertion and deletion, while still rolling back if the room or message changed, disappeared, or the second write fails. It does not weaken chat authorization. Already-applied receipt batches retain the existing zero-data-write path. Group chats, legacy-only rooms, root messages, multiple messages, transforms, and other shapes retain their old guards and compatibility paths.

In local Miniflare with real Worker routes and isolated synthetic data, the first receipt and unread reset went from **9 reads / 10 writes / 7 statements to 7 / 8 / 5**; a duplicate remained **3 / 0 / 3**. This is a limited optimization, not a complete quota fix or proof that it addresses the reported peak. Tests cover forbidden actors, altered/deleted room and message, rollback of second-write failure, duplicates, group ledger, legacy room, and historical root-message mirror. All 219 Worker tests and nine schema/migration/index tests passed locally.

## Why one app action is not necessarily one D1 row

The same isolated Worker experiment measured a five-card Feed page at 44 reads and zero writes, a new like at 7 reads / 4 writes, a new comment at 10 / 9, a direct message+room update at 4 / 10, and a typing poll at 5 / 0. Duplicate like/comment and immediate repeated typing reported zero writes. D1 maintains indexes, totals, related room/receipt rows and authorization/privacy checks, so one user action may legitimately involve several rows. These fixtures exclude push delivery, real devices and production data; they are neither an estimate of the five users' actual actions nor account-wide billing.

A hard global request cap or cached authorization could cause failed messages, missing notifications or privacy leaks and would not make a finite Free quota unlimited. The current typing, presence and push paths already have bounded/no-op behavior; blindly slowing them would make real-time indicators stale. Further work requires attribution during actual normal usage, including installed app versions, and safe investigation of index maintenance or query plans. Do not remove production indexes or issue unbounded preflights while quota headroom is unknown.
