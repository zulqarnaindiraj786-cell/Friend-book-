# Notification recipient-index candidate (compatibility only)

The recent adaptive five-minute audit included two insert shapes at 88 executions / 792 reported rows written each; their shapes are shared and do not prove notification creation is their source. The optimization below was found by inspecting notification indexes, not by attributing those shapes. The latest delayed account-wide analytics at 08:44:59 UTC reported 1,163,752 daily reads and 51,825 daily writes, not a guaranteed current billed balance.

Both old recipient-only indexes appear to be prefixes of the canonical and legacy notification page indexes. A compatibility Worker now pins the unbounded canonical all-notification recipient query to `idx_cf_notif_page` (the unread query continues to pin `idx_cf_notif_unread`). Missing indexes retain the previous unhinted fallback. Without the pin, local SQLite selected the broad parent-path index after removal of the canonical recipient-only index, potentially scanning all inboxes. The legacy compatibility path chose `idx_cf_legacy_notif_page` in the tested SQLite fixture when its recipient-only index was removed. This Worker change does **not** drop indexes or itself establish any write savings.

Local tests with 1,000 mixed canonical/mirrored/legacy notifications include wrapped records, inbox visibility, unbounded and paginated reads, unread/count paths, cursors and missing-index fallback. In a separate local real-Worker comparison the old and new code returned identical serialized results for these requests. After experimentally dropping both recipient-only indexes, local result and privacy tests still passed and the replacement plans sought recipients. Local Miniflare with the real Worker and schema through 0081 measured one create-only unread notification at **1 read / 18 writes / 4 statements** before versus **1 / 16 / 4** after experimentally dropping both indexes; duplicate retry stayed **2 / 0 / 2**, and concurrent create, mirror rollback and unauthorized sender tests passed. Miniflare D1 metadata is not production billing, and live notification distribution and savings are unknown.

No production index is dropped in this change. Removing them requires separate bounded, read-only production preflight, broader compatibility and query-plan review, an explicit guarded migration and rollback plan, account budget/headroom checks and a staged deployment. Existing or external consumers and pre-compatibility Workers might select a broad scan; re-creating indexes can itself consume quota. No guarantee of free capacity or a solved quota issue follows from this candidate.
