# Notification quota triage

The user's November 22 screenshots show account dashboard totals rising from 21.77k reads / 1.03k writes at 05:04 to 97.63k reads / 8.35k writes at 05:13. That is an apparent increase of 75.86k reads and 7.32k writes in about nine minutes, subject to dashboard delay/rounding. The later screenshot is about 1.95% of 5M daily reads and 8.35% of 100k daily writes, not quota exhausted. Dashboard counters aggregate usage; the difference cannot be attributed to one user's actions, the deployment, migration index builds, or a particular query without matched telemetry.

Read-only D1 analytics run 44966043991 reports the top shapes for the **database** and window, not the screenshot's entire account or a single installation. In its latest 15 minutes, two notification-related read shapes totaled 7,614 rows / 126 executions and 3,840 rows / 120 executions respectively. They may be parts of the same operation and should not be interpreted as independent user requests. Adaptive analytics and dashboard counters have different aggregation and timing. Other significant shapes include point reads and engagement. The top write shapes aggregate canonical/legacy document mutations and temporary guards; they do not identify which user or feature caused them.

The notification page now fetches the same bounded canonical and legacy windows. A legacy item whose path is already in the canonical window is known to be shadowed, so it needs no extra canonical D1 point lookup. Remaining unknown paths are checked in one bounded primary-key query, preserving canonical precedence even when a legacy copy has different ownership, read state, or ordering. No schema changes or index backfills are required. Full-mirror tests show no extra shadow query; mixed/legacy and stale-ownership, stale-read, stale-order cases remain covered. This targets read amplification in notification pages for all compatible existing clients; it doesn't reduce necessary writes and doesn't imply every notification query is covered.

The local test verifies lookup behavior and correctness, not D1 billed rows. Compare matched production query windows after deploy to evaluate savings; do not infer them from test result counts or from the earlier screenshot. Quota exhaustion cannot be ruled out: growth, write amplification, other query paths, request volume and multiple users still matter. Avoid synthetic production load or repeated write probes.
