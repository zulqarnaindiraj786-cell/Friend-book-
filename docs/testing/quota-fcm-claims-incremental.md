# Incremental FCM claims without copying existing data

In the 09:50 UTC 2026-11-22 five-minute adaptive sample, per-device FCM claim INSERTs reported 132 written rows / 66 executions. These are adaptive query analytics, not a measurement of total account billing or proof that notifications caused the entire spike. Claims suppress duplicate pushes and incoming calls, so they must not be removed or bypassed.

## Approach

Migration 0085 creates an **empty** `WITHOUT ROWID` claim table and a legacy-table `BEFORE INSERT` bridge trigger. It does not copy, scan, delete, or rewrite old claims, and it does not build an index over historical application rows. New Worker versions insert a new key only if it does not already exist in the legacy table, in the same SQLite statement. The trigger makes old Worker versions and rollback attempts skip a legacy insert when the new table already holds that key. Both claim paths use atomic primary-key uniqueness; no persisted claim is discarded. Failed FCM delivery releases only the table claimed by that attempt, preserving existing retry and unregistered-device handling. The pre-migration Worker path remains the fallback only when the new table does not yet exist; other storage errors fail closed.

Local Miniflare D1 with the actual schema measured a unique old-style claim at **0 reads / 2 writes**, and a new-style claim at **0 / 1**; a repeated new-style claim was **0 / 0**. The two metadata-only DDL statements measured 1 read / 3 written rows combined in the isolated fixture. These numbers exclude remote migration bookkeeping and are not a live account billing guarantee. Concurrent old/new claim attempts, old-first/new-first/rollback ordering, provider failure and retry, device invalidation, pre-migration fallback, unrelated old claims and per-device isolation were tested locally. The full Worker suite passed 222 tests, and schema/migration/index tests passed. No synthetic production sends or claim deletion were performed.

## Deployment and rollback safety

For this branch the rollout requires explicit `[fcm-bridge-only]` opt-in. The deployment rejects unexpected pending migrations, checks account analytics against a reserve specific to this metadata-only change (at most 3M reads / 75k writes reported; analytics may lag and cannot guarantee available quota), and verifies the legacy table, new table and exact bridge-trigger schema after migration and on every later deployment before deploying the Worker. The existing more conservative 50k-write safety threshold for unknown-cost/index-build preflights remains unchanged. The post-migration verification scans SQLite schema metadata only, not user records; an isolated fixture reported about 234 reads, but actual remote D1 cost is not guaranteed. If any gate fails, the Worker is not deployed. A partially applied migration must be verified before retrying; with the old Worker and an empty new table, existing claims remain authoritative.

Rollback to the previous Worker requires **retaining both new table and bridge trigger**: old Workers use the trigger to respect keys already in the new store. Do not drop either while any new-store claims may be retried, and do not copy or erase old claims merely for rollback. Schema changes, concurrent other production jobs and external writers are outside the local tests. A physical device/FCM delivery test and matched real production usage are still needed. This change saves at most one indexed write per newly acquired per-device claim; it does not halve total D1 usage, guarantee every push, or solve the whole quota issue by itself.
