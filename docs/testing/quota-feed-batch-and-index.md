# Feed count consolidation and legacy name index

The read-only production analytics snapshot 44976782511 at 02:35:13 UTC reported, in its preceding five-minute sample, two comment/reaction summary shapes with 1,020 reads/68 executions and 933 reads/78 executions, plus a legacy comment shape with 684 reads/171 executions. These are adaptive samples; SQL shape alone does not establish the caller or feed-page limits. The UTC-day adaptive aggregate was 118,702 executions, 281,772 reads and 17,901 writes for this database, not account-wide dashboard billing. The snapshot is too short and activity is uncontrolled, so it cannot demonstrate the effect of the previous deploy.

The Worker now combines a bounded Feed page's per-resource legacy comment counts into one compound statement with the same indexed predicates and per-resource canonical shadow and blocked-author checks. Canonical summaries remain independent statements in the same atomic D1 batch; existing individual fallback remains when the batch is unsupported or incomplete. A 20-card batch uses 21 rather than 40 SQL statements, with 41 bound parameters and a 66,923-byte statement. The Home request is still five posts, and later posts still require intentional scroll. No comments, privacy checks or result limits are removed. A production workload may still read the same number of underlying rows: fewer statements do not establish billed-row savings.

An offline real-Worker replay of 999 five-post Feed requests over 1,000 synthetic accounts and waves of up to 200 overlapping operations changed SQLite statements from 24,975 to 20,979; returned rows remained 42,957 and both runs changed zero rows. These are local statement/result counts, not Cloudflare billing. Regression tests compare grouped counts and Feed summaries with the original independent paths for multiple resources, wrapped documents, duplicate references, blocked authors, deletions, canonical shadows and response mapping. SQLite query plans use all three existing legacy-comment lookup indexes.

Migration 0075 removes only obsolete `idx_cf_legacy_users_display_name`. The currently deployed Worker uses `idx_cf_legacy_people_cursor_prefix`, which supports both plain and historical envelope names, and retains the canonical name index. On 1,000 synthetic legacy-user updates, local SQLite VM instructions changed from 695,000 to 668,011; this is not a measured D1 write saving. The migration is repeatable and plan tests confirm the replacement remains. One-time index removal can itself use D1 quota. For rollback to an older Worker that explicitly references the removed index, first recreate that index using migration 0053's `CREATE INDEX` statement; older versions must not be deployed against the new schema without it.
