# Group-post atomic snapshot quota follow-up

For an existing canonical group post with a canonical group, authorization still checks membership, bans, roles and server-owned group owner. The write batch now compares the exact previously authorized post, group and trusted owner snapshots inside the canonical upsert. A mismatch raises a NOT NULL constraint error, rolls the entire batch back and causes the usual post mutation to re-read and reauthorize. Canonical post, app mirror and interaction-resource verification are still committed together. Creates, deletes, legacy-only group or post records retain the previous guard path. Missing/staging interaction-resource markers are still promoted to verified. There is no schema or Android change.

Actual Worker handlers on synthetic Miniflare D1 using migrations through 0081 measured one canonical group-post edit with a verified marker at **15 reads / 24 writes / 11 statements** before, and **15 / 18 / 7** after. The six fewer writes are the three temporary guards and their deletion; genuine post/mirror and indexed trigger writes remain. In the separate offline SQLite Worker replay, 1,000 distinct edits used **11,000 -> 7,000 statements**, **29,633 -> 23,633 changed rows including triggers**, with **4,000 returned rows** both times. SQLite changed rows do not include index maintenance. Neither result establishes production billed savings or feature frequency.

Tests cover membership revocation, trusted-owner revocation and concurrent post edits during the batch, forbidden edits, approval transitions, verified/staging markers, failures of mirror and resource-marker writes with rollback, and both legacy group and post paths. Miniflare additionally tested the membership, owner and post races and injected mirror failure. The complete replay executed 35,489 requests and 63 query plans without EXPLAIN errors; locally 189 Worker, nine schema/plan and 280 script tests passed. Run `QUOTA_QUERY_PLANS=1 node scripts/loadtest/d1_quota_replay.mjs 1000 1` and compare `groupPostEdit` with the preceding revision in an isolated checkout to reproduce the SQLite comparison. Local testing is not a device test or a guarantee against quota exhaustion. No production test traffic was created. Rollback is the previous Worker version; no data migration is needed.
