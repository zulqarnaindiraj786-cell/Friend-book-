# Chat membership trigger write reduction

When Android replies in a direct chat, it may serialize the same two members in reverse order. The old 0058 triggers treated this as a membership change and deleted and reinserted every derived membership row in both the canonical and legacy stores. This is separate from the actual message, room and mirror writes. The historical 15-minute analytics sample of 24,388 reads on a chat-membership join does not identify the frequency of reversed replies and does not prove this change's production savings.

Migration 0083 replaces four membership insert/update triggers without rebuilding or deleting the membership table or either index. It reconciles membership as a set, deleting only obsolete entries and inserting missing entries. A simple reversed two-person array has a faster path only when the indexed set is already exactly correct; missing or extra entries are repaired instead. Legacy Firestore-wrapped members use their original representation, not conflicting root fields. Explicit UPSERT conflict handling also tolerates duplicate historical participant values under outer document upserts. Existing delete triggers, authoritative room checks, message delivery and call handling remain unchanged. No Worker or Android change is needed for this server-side fix.

On local Miniflare D1 through migration 0082, the actual Worker direct-send batch with unchanged order used **4 reads / 11 writes / 5 statements** both before and after. A reverse-order reply with both room representations used **14 reads / 29 writes / 6 statements** before and **14 / 13 / 6** after. It still inserted the message, updated room metadata and mirror, and preserved both membership sources. Actual Worker race, membership revocation, mirror failure and rollback checks also passed locally. These are synthetic local D1 metadata, not actual billed production usage.

An isolated single-table, 100-member room update measured 203 reads / 405 writes for adding one member under the old trigger versus 506 / 5 with the new one. Removing two members after that measured 202 / 400 versus 503 / 4. This demonstrates a **read/write trade-off** on large membership changes; it is not a full group-chat request or a billing forecast. The no-rebuild trigger migration itself incurs DDL cost, not a table backfill. Lists, results, call freshness and access-control checks are not capped or disabled.

Offline real-Worker SQLite replay of 500 reverse replies used **3,000 statements and 1,000 returned rows** in both versions, with **5,500 to 1,500 changed rows including triggers**. SQLite change counts exclude index maintenance. Reproduce with `QUOTA_FORCE_CHAT_MEMBERS_BASELINE=1 node scripts/loadtest/d1_quota_replay.mjs 1000 1` and the same command without the flag. A 38,488-request run and a separate wave of up to 200 concurrent requests (serialized local SQLite commits) passed, and 63 collected query plans had no EXPLAIN errors. Locally 190 Worker, nine schema/plan and 280 script tests passed.

Regression tests compare old and new derived sets on random mutations, additions/removals, duplicate and malformed members, wrapped records with conflicting root fields, both storage sources, path changes, deletion, and stale/missing index repair. Applying 0083 twice preserves existing index rows. Do not rebuild the membership table to roll back: restore the 0040 insert triggers and 0058 update triggers while retaining the existing table and indexes; that rollback restores write amplification and historical duplicate-value upsert failures. Real-device behavior and production billed savings remain unmeasured. No production synthetic messages or test pushes were generated.
