# Follow transaction and membership-trigger conflict

## Functional bug found while measuring

A real-Worker local replay with the 0078 membership triggers exposed a pre-existing failure: a follow can return 409 when either user already has indexed follower/following entries. An outer document `INSERT ... ON CONFLICT DO UPDATE` overrides a trigger's `INSERT OR IGNORE` conflict policy, so inserting an already-indexed membership can instead raise a uniqueness error. The whole transaction rolls back; this is not evidence of silent partial writes. This was reproduced in both SQLite and Miniflare D1 with actual Worker code, including the preceding deployed revision. Its production frequency is unknown.

Migration 0082 replaces only the four insert/update membership triggers with equivalent trigger bodies using explicit `ON CONFLICT(member,kind,source,path) DO NOTHING`. It does not delete, rebuild or backfill the index or change its readiness marker; the delete triggers, tables and indexed query compatibility remain. Explicit UPSERT conflict clauses survive the outer upsert. Applying the trigger replacement twice preserved all synthetic index rows and readiness. Tests cover duplicate values, canonical and legacy mirrors, indexed versus full-scan answers, exception records, updates/removals and long arrays. Local Miniflare confirmed that a follow with an existing edge failed with old triggers and succeeded with the replacement. The migration is DDL and has a production cost, but it does not scan or rewrite the existing membership data. Production D1 billing and live incidence are not measured. Rolling back this trigger fix to 0078 reintroduces the conflict; older Workers may safely use the corrected triggers.

## Quota change

When both follow profiles are canonical, the first canonical upsert checks both exact authorized snapshots in the D1 batch. Both profiles and mirrors still commit atomically. A concurrent profile/block change raises the same 409 contract as the old guard; clients must retry. Any historical-only profile uses the existing conversion and guard path. No authorization, push or index membership semantics are deliberately changed.

On local Miniflare D1 with schema through 0081 and corrected 0082 triggers, one follow where the actor already had an edge measured **28 reads / 44 writes / 12 statements** with the old Worker and **26 / 40 / 7** with the candidate. The four fewer writes are the two temporary guard inserts and their deletion. Local D1 metadata includes index activity and does not establish billed production usage. A concurrent block returned 409 without updating either relationship; two concurrent follows returned 200 and 409 with both profiles consistent; an injected mirror failure rolled back all earlier writes.

An offline Worker/SQLite replay of 500 follows with corrected triggers measured **6,000 -> 3,500 statements**, **2,500 -> 1,500 returned rows**, and **6,000 -> 4,000 changed rows including triggers**. SQLite changed-row counts do not include index maintenance. The full replay executed **37,988 requests**, including a wave of up to 200 against serialized local SQLite, and 63 query plans without EXPLAIN errors. Locally 189 Worker, nine schema/plan and 280 script tests passed. Worker tests cover forbidden actors, friendship changes, block races, mirror rollback and legacy-only promotion. Run `QUOTA_QUERY_PLANS=1 node scripts/loadtest/d1_quota_replay.mjs 1000 1`; to compare the old Worker, copy both the replay workload and 0082 to an isolated preceding checkout. Device behavior and production savings are unmeasured; no production synthetic traffic was generated. Reverting the Worker alone can keep 0082 installed.
